# ADR 0001: Frontend stack for FE-001 (Auth screens)

## Status
Accepted

## Context
FE-001 requires building Login, Register, and Forgot Password screens with
client-side validation only (no API, no backend). The screens must be built
from a consistent design system with reusable components, since cart,
checkout, and profile will reuse the same shared UI.

## Decision

**Framework:** React + Vite + TypeScript
- Vite gives fast dev server startup and HMR.
- TypeScript catches prop/field-name mismatches at compile time, which
  matters here because form field names must match Zod schema keys exactly.

**Forms:** React Hook Form + Zod (via `@hookform/resolvers/zod`)
- React Hook Form keeps re-renders minimal and gives direct access to
  `setFocus`, which is used to jump to the first invalid field on submit.
- Zod schemas double as the single source of truth for both validation
  rules and TypeScript types (`z.infer`), avoiding duplicated field
  definitions between validation logic and form types.
- Validation mode: `onSubmit` first, then `onChange` after the first
  failed submit, matching the ticket's requirement to validate on submit
  and re-validate on change afterward.

**Styling:** Plain CSS with CSS custom properties as design tokens
- All colors, spacing, radii, typography and the focus-ring effect are
  defined once in `src/shared/tokens/tokens.css` and consumed via
  `var(--token-name)` everywhere else. No component hardcodes a color or
  spacing value.
- This was chosen over a CSS-in-JS or utility-class framework to keep the
  dependency footprint small for a markup-and-validation-only ticket, and
  because token-driven plain CSS maps directly onto Figma's token scale.

**Shared UI kit:** `src/shared/ui/`
- `Button`, `Input`, `PasswordInput`, `FormField`, `Alert` — each built to
  be reused as-is by Cart, Checkout, and Profile, per the ticket's
  requirement.
- `Input` and `PasswordInput` use `forwardRef` so React Hook Form's
  `register()` can attach directly to the underlying DOM node (required
  for `setFocus` to work).
- `FormField` centralizes the label + input + error-message pattern once,
  rather than repeating that markup in every form.

**Routing:** `react-router-dom`, using `createBrowserRouter`.

**Server state (deferred):** TanStack Query is not yet installed. There is
no API in this ticket's scope; it will be introduced when a real backend
is wired up (cart/checkout/profile or an auth API).

## Consequences
- Any future page reusing `shared/ui/` components must not introduce
  one-off style overrides that bypass the token system — new colors or
  spacing must be added as tokens.
- Since there's no API yet, the "successful submit" behavior in all three
  screens is a simulated `setTimeout` + `console.log`. This will need to
  be swapped for real API calls once a backend exists, but the loading
  state and error-handling structure are already in place to support that
  swap with minimal changes.



  
## Update (FE-002): Token storage — localStorage vs httpOnly cookie

**Decision:** The access token is stored in `localStorage` (see
`src/shared/lib/token.ts`), not an httpOnly cookie.

**Why:**
- This ticket's backend is a stateless REST API that expects the token to
  be sent manually via an `Authorization: Bearer <token>` header on every
  request (see `src/shared/api/client.ts`). An httpOnly cookie is sent
  automatically by the browser and cannot be read or attached to headers
  by JavaScript, so using one would require the backend to support
  cookie-based auth (setting the cookie on login, reading it via
  `Set-Cookie`/`Cookie` headers), which this API does not do.
- `localStorage` persists across page refreshes and browser restarts
  without any extra server support, matching the ticket's requirement
  that a refresh does not flash the login screen for an already-logged-in
  user (see the three-state `AuthContext` in `src/app/AuthContext.tsx`).

**Risk accepted:** `localStorage` is readable by any JavaScript running on
the page. If the app is ever vulnerable to XSS (e.g. through an unescaped
render of user-generated content, or a compromised third-party script),
an attacker's injected script can read `localStorage` directly and steal
the access token, impersonating the user until the token expires (30
minutes per the ticket). An httpOnly cookie would not be readable by
injected JavaScript at all, so it is the stronger choice against XSS
specifically — but it shifts the responsibility for CSRF protection onto
the server instead, and requires backend support this API doesn't offer.

**Mitigations already in place:**
- The token has a short lifetime (30 minutes, enforced server-side), which
  limits how long a stolen token remains useful.
- The token is never logged, rendered into the DOM, or included in URLs.
- React's default JSX escaping (`{value}` is text-escaped, not
  `dangerouslySetInnerHTML`) is used everywhere in this app, which is the
  primary practical defense against the DOM-based XSS that would make
  this risk exploitable in the first place.

**If the backend changes** to support httpOnly cookies in the future,
switching to that model would only require changes to
`src/shared/lib/token.ts` and the `Authorization` header logic in
`src/shared/api/client.ts` — the rest of the app (forms, `AuthContext`,
protected routes) would not need to change, since token storage is
already isolated behind that one module per the original ADR's design.


## Update (FE-005): Handling fast clicks on the quantity stepper

**Decision:** While any cart request is running, all `+`, `−` and delete
buttons on the cart page are disabled (`isBusy`). The user cannot send a
second request until the first one returns.

**Why:**
- Three quick clicks on `+` would fire three parallel PATCH requests. They
  can come back in a different order, so the screen could show 2 instead
  of 4. Disabling the buttons prevents this by construction.
- It is simple and reliable. There is no debounce timer to tune and no
  rollback logic to write.
- Each request returns the whole updated cart, which we write straight
  into the `['cart']` query cache. The cart has one source of truth, so the
  header badge and the cart page always agree.

**Trade-off accepted:** A debounce (300ms) would feel smoother when someone
wants to jump from 1 to 10 quickly, because only the last value is sent.
We chose correctness and simplicity over that speed.

**Related decisions:**
- Totals (`lineTotal`, `subtotal`) come from the server and are never
  calculated on the frontend, so two places can never disagree.
- On logout and on token expiry the `['cart']` cache is removed, so the
  next person on the same browser never sees the previous cart. The cart
  itself stays on the server.
- `productId` is used only for adding to the cart. `PATCH` and `DELETE`
  use the cart line id (`items[].id`).
